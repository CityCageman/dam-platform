# 生产部署方案（2 台 · 麒麟 V10 · x86_64 · 外部数据库 · 纯内网）

> 更新：2026-11-01
> 已确认条件：
> - 两台服务器均为 **x86_64 麒麟 V10**
> - **无构建机**、**纯内网**（无法拉取镜像/Maven/npm）
> - 数据库沿用现有 **`10.162.3.16:11001`**（TBase / PG10 内核），两台都不装数据库
> - LLM 服务**内网可达**
> - 演示账号**保留不删**
>
> 因此最终采用 **裸机 systemd**，不使用容器。可执行产物见 `dam-release/`（部署包）。

---

## 1. 为什么不用容器

容器方案的前置是基础镜像（`eclipse-temurin:21-jre`、`nginx`）。当前没有构建机、没有内网镜像仓库、没有可联网环境，基础镜像拿不到；而裸机只需要 **JDK 21 + Nginx**，两者都能离线提供。

| 项 | 裸机（本方案） | 容器（原 `deploy/podman`） |
|---|---|---|
| 离线依赖 | JDK tar + jar | 基础镜像 tar（架构必须匹配） |
| 升级 | 替换 jar + restart | 重建镜像 + load |
| 资源 | 10 个 JVM | 10 个容器（+5~10% 开销） |

## 2. 两台服务器分工

| 服务器 | 角色 | 建议配置 | 承载 | 端口 |
|---|---|---|---|---|
| A 应用机 | 后端 | 8C / 16G / 200G | 10 个 Spring Boot 服务（systemd） | 8080 仅放行 B；8081–8093 不对外开放 |
| B 前端机 | 前端 + 运维 | 4C / 8G / 100G | Nginx（静态资源 + 反代 A:8080）、备份 | **80 对内网开放** |

不部署 Nacos：`SPRING_CLOUD_NACOS_*_ENABLED=false`，网关用 `DAM_ROUTE_*` 直连 `127.0.0.1`。

## 4. 部署步骤（摘要）

### 4.1 A 机（后端）

```bash
tar xzf dam-release-20261101.tar.gz -C /opt
cd /opt/dam-release
bash scripts/install-app.sh          # 首次会生成 /etc/dam/env.conf 并停止
vi /etc/dam/env.conf                 # 改 DB 口令、JWT 密钥、LLM Key
bash scripts/install-app.sh          # 再次执行：装 JDK、拷 jar、启服务
bash scripts/verify.sh app
```

`install-app.sh` 会自动：装 JDK 21 到 `/opt/jdk21` → 建 `dam` 用户 → 拷 10 个 jar → 安装 systemd → 按 **业务服务 → 网关** 顺序启动。

### 4.2 B 机（前端）

```bash
tar xzf dam-release-20261101.tar.gz -C /opt
cd /opt/dam-release
bash scripts/install-frontend.sh <A机内网IP>
bash scripts/verify.sh web <A机内网IP>
```

### 4.3 防火墙

```bash
# A 机：8080 只放行 B
firewall-cmd --permanent --add-rich-rule='rule family=ipv4 source address=<B机IP> port port=8080 protocol=tcp accept'
firewall-cmd --reload
# B 机：80
firewall-cmd --permanent --add-port=80/tcp && firewall-cmd --reload
```

## 5. 必改配置（`/etc/dam/env.conf`）

| 键 | 说明 |
|---|---|
| `SPRING_DATASOURCE_PASSWORD` | 现有库 `dam` 用户口令（不再写死在 yml） |
| `DAM_CORS_ORIGINS` | 前端来源，如 `http://<B机IP>`；同源反代可不配 |
| `SA_TOKEN_JWT_SECRET_KEY` | `openssl rand -base64 48`；**所有后端服务必须一致**，通过环境变量注入 |
| `SPRING_DATASOURCE_URL` | 默认已是 `jdbc:postgresql://10.162.3.16:11001/damplatform` |
| **`DAM_SECURITY_CRYPTO_SECRET`** | **不要改**：必须与现有库中数据源口令的加密密钥一致，改了会导致已存的数据源口令解不开 |

## 6. 上线前必须知道的风险

1. **网关已启用 JWT 验签**：`SaTokenConfig` 使用 `StpLogicJwtForStateless` + `StpUtil.checkLogin()`，签名错误/过期/伪造 token 返回 401。
   - 所有后端服务必须配置**相同**的 `SA_TOKEN_JWT_SECRET_KEY`，否则跨服务会报 token 无效；
   - 仍建议用防火墙把 8080 限制为只允许 B 机访问，作为第二道防线。
2. **演示账号保留**（按要求）：登录页会显示并默认填充 `admin/admin123` 等。
   - 建议上线后立即改这三个账号的密码；
   - 系统只在内网开放，不要映射到公网。
3. **数据库脚本不要用于生产**：`db/create_schema_doc.sql` 的 schema 名与代码不符；`db/init-all.sql` 的初始口令是 SHA-256 而登录用 BCrypt。沿用现有库即可避开。
4. **现有库需确认 schema 版本**：检查 `dam_asset.asset_category_rel`（v2）与 `dam_asset.report_catalog`（v3）是否存在，缺则执行 `db/v2_subject_domain.sql`、`db/v3_report_system.sql`。
5. **数据源 AES 密钥**：见 §5，切勿更换。

## 7. 验收

见 `dam-release/README.md` 第 6 节，核心 4 条：

```bash
systemctl status 'dam@*' --no-pager
curl -s -o /dev/null -w '%{http_code}\n' http://127.0.0.1:8080/api/auth/public-key   # 200

# 浏览器打开 http://<B>/ 能登录
```

## 8. 后续重新构建

本产物是在一台 JDK 21 + Maven + Node 的机器上构建的（jar/dist 与 CPU 架构无关，可直接部署到 x86_64 Linux）。
以后重新构建只需任一有 JDK 21 / Maven / Node 的机器：

```bash
cd dam-platform
bash deploy/build.sh
```

产出 `codebase/backend/*/target/*-exec.jar` 与 `codebase/frontend/dist/`，替换部署包中的对应目录即可。
建议备份该构建机的 `~/.m2` 与 npm 缓存，便于将来在纯内网重建。

## 9. 运维

- 日志：`/opt/dam/logs/*.log`，建议 logrotate 保留 30 天。
- 启停：`systemctl restart dam@dam-catalog`、`systemctl restart 'dam@*'`。
- 升级：覆盖 `/opt/dam/*.jar` → `systemctl restart 'dam@*'`。
- 回滚：保留上一版 jar，覆盖后重启；数据库配合备份。
- 备份：`pg_dump -h 10.162.3.16 -p 11001 -U dam -Fc -d damplatform`。
